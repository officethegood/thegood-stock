## Task A1 — Tighten `apply_movement_to_lot_qty` search_path

**Source:** Audit S-4 (MEDIUM). The function's `SET search_path = public, pg_temp` includes `pg_temp` which is unnecessary for this function's logic and expands its blast radius slightly. This migration drops `pg_temp` from the path.

**File to create:** `supabase/migrations/20260519020000_tighten_lot_qty_search_path.sql`

**Why:** Per S-4, `apply_movement_to_lot_qty` only reads/writes `stock_lots`. Removing `pg_temp` from its search_path reduces the attack surface in the event the function body is ever modified. This is a defence-in-depth hardening step with zero functional change.

**Migration SQL:**

```sql
-- Migration: 20260519020000_tighten_lot_qty_search_path.sql
-- Purpose: Remove pg_temp from apply_movement_to_lot_qty SECURITY DEFINER function
--          to shrink its blast radius (Audit S-4 MED finding).
-- Idempotent: CREATE OR REPLACE is always safe.
-- Ref: docs/superpowers/audits/2026-05-19-phase2-security.md §S-4

CREATE OR REPLACE FUNCTION apply_movement_to_lot_qty()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public          -- removed pg_temp (was: public, pg_temp)
AS $$
DECLARE
  v_new_lot_qty  integer;
BEGIN
  -- Only act when lot_id is set and qty_delta is non-zero.
  IF NEW.lot_id IS NULL THEN
    RETURN NEW;
  END IF;

  -- Decrement or increment stock_lots.current_qty atomically.
  UPDATE stock_lots
     SET current_qty  = current_qty + NEW.qty_delta,
         updated_at   = now()
   WHERE id = NEW.lot_id
  RETURNING current_qty INTO v_new_lot_qty;

  -- Auto-deplete when current_qty reaches zero.
  IF v_new_lot_qty IS NOT NULL AND v_new_lot_qty = 0 THEN
    UPDATE stock_lots SET status = 'depleted', updated_at = now()
     WHERE id = NEW.lot_id AND status = 'active';
  END IF;

  -- Negative qty guard — CHECK constraint on stock_lots also fires, but this
  -- provides a cleaner error message. (Audit S-14: guard fires AFTER UPDATE,
  -- so the CHECK constraint may surface first for extreme negatives — acceptable.)
  IF v_new_lot_qty IS NOT NULL AND v_new_lot_qty < 0 THEN
    RAISE EXCEPTION 'lot current_qty would go negative';
  END IF;

  RETURN NEW;
END;
$$;

COMMENT ON FUNCTION apply_movement_to_lot_qty() IS
  'SECURITY DEFINER — only reads/writes stock_lots. search_path restricted to public only (no pg_temp). See audit S-4.';
```

Verify the logic inside the BEGIN..END block matches the production version exactly before replacing. If there are additional columns being set (e.g. `updated_by`), carry them forward. The block above is the canonical Phase 2 version from migration `20260519010500`; confirm no hotfix has changed it.

## Task A2 — Add `recalled_reason` NOT NULL constraint (S2-B) + lot immutability trigger (S-11)

**Source:** Audit S-11 (LOW) — Admin can UPDATE `lot_number`, `item_id`, `received_qty` on `stock_lots`, destroying audit trail. Combined with a small S2-B check to enforce substantive recalled_reason.

**File to create:** `supabase/migrations/20260519020100_recalled_reason_required.sql`

**Why:**
- S-11: An admin could clear `recalled_reason` or change `lot_number` after a recall, erasing the audit record. A BEFORE UPDATE trigger that blocks changes to the three immutable columns closes this.
- S2-B spec: When status is set to `recalled`, `recalled_reason` must be provided and meaningful (length >= 5 chars). Enforced as a partial column-level CHECK constraint.

**Migration SQL:**

```sql
-- Migration: 20260519020100_recalled_reason_required.sql
-- Purpose:
--   1. Add partial CHECK ensuring recalled_reason is non-null and >= 5 chars when status='recalled'.
--   2. Add BEFORE UPDATE trigger preventing modification of immutable columns
--      (lot_number, item_id, received_qty) on stock_lots.
-- Idempotent: uses IF NOT EXISTS / DO blocks / CREATE OR REPLACE.
-- Ref: docs/superpowers/audits/2026-05-19-phase2-security.md §S-11, §S2-B

-- -------------------------------------------------------------------------
-- Step 1: Add the recalled_reason length check as NOT VALID
--         (NOT VALID means existing rows are not checked on ALTER — safe for
--          zero-row or any-row tables. Must VALIDATE separately in Step 2.)
-- -------------------------------------------------------------------------
DO $tag$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM pg_constraint
    WHERE  conrelid = 'stock_lots'::regclass
      AND  conname  = 'chk_recalled_reason_required'
  ) THEN
    ALTER TABLE stock_lots
      ADD CONSTRAINT chk_recalled_reason_required
      CHECK (
        status <> 'recalled'
        OR (recalled_reason IS NOT NULL AND length(recalled_reason) >= 5)
      )
      NOT VALID;
  END IF;
END
$tag$;

-- -------------------------------------------------------------------------
-- Step 2: Validate the constraint against existing rows.
--         If this fails, rows exist with status='recalled' and short/null reason.
--         Inspect: SELECT * FROM stock_lots WHERE status='recalled'
--                                             AND (recalled_reason IS NULL
--                                                  OR length(recalled_reason) < 5);
-- -------------------------------------------------------------------------
ALTER TABLE stock_lots
  VALIDATE CONSTRAINT chk_recalled_reason_required;

-- -------------------------------------------------------------------------
-- Step 3: Immutability trigger — prevent modification of audit-critical columns.
--         Pattern mirrors prevent_lot_delete() recommendation in audit S-7 (already
--         deployed in Phase 2 migration). See audit S-11.
-- -------------------------------------------------------------------------
CREATE OR REPLACE FUNCTION prevent_lot_immutable_update()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  IF OLD.lot_number  IS DISTINCT FROM NEW.lot_number THEN
    RAISE EXCEPTION 'stock_lots.lot_number is immutable after creation';
  END IF;
  IF OLD.item_id     IS DISTINCT FROM NEW.item_id THEN
    RAISE EXCEPTION 'stock_lots.item_id is immutable after creation';
  END IF;
  IF OLD.received_qty IS DISTINCT FROM NEW.received_qty THEN
    RAISE EXCEPTION 'stock_lots.received_qty is immutable after creation';
  END IF;
  RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS trg_no_update_lot_immutable ON stock_lots;
CREATE TRIGGER trg_no_update_lot_immutable
  BEFORE UPDATE ON stock_lots
  FOR EACH ROW EXECUTE FUNCTION prevent_lot_immutable_update();

COMMENT ON FUNCTION prevent_lot_immutable_update() IS
  'Guards lot_number, item_id, received_qty from UPDATE after creation. See audit S-11.';
COMMENT ON CONSTRAINT chk_recalled_reason_required ON stock_lots IS
  'When status=recalled, recalled_reason must be non-null and at least 5 characters long. See audit S2-B.';
```

**Verification (run after deploy):**

```sql

  AND  conname  = 'chk_recalled_reason_required';
-- Expected: 1 row, convalidated = true

-- Confirm trigger exists

WHERE  tgrelid = 'stock_lots'::regclass

ROLLBACK;

```

## Task B5 — P6: `searchByBarcode` — switch `.eq` to `.ilike` for partial barcode matching

**File:** `shared/inventory.js`

**Problem (backlog item #6):** `searchByBarcode` uses `.or(`barcode.eq.${v},sku.eq.${v}`)` (exact match). EAN-13 and UPC-A variants of the same product may differ in prefix digit (e.g., `8851234567890` vs `1851234567890`). Case-insensitive partial match catches these. The spec allows `.ilike` for the scan fallback path (T35/T36 note: "Phase 1.1" deferred).

**Pattern reference:** `_queryItemsView()` in same file (line 165–168) already uses `.ilike` for the `search` parameter.

**Exact change in `shared/inventory.js` — find `searchByBarcode` function (lines 226–239):**

Find:
```javascript
      const r = await sb.from('stock_items')
        .select('id,sku,barcode,name,name_en,category_id,unit,reorder_threshold,active')
        .or(`barcode.eq.${v},sku.eq.${v}`)
        .eq('active', true)
        .limit(1);
```

Replace with:
```javascript
      const like = `%${v}%`;
      const r = await sb.from('stock_items')
        .select('id,sku,barcode,name,name_en,category_id,unit,reorder_threshold,active')
        .or(`barcode.ilike.${like},sku.ilike.${like}`)
        .eq('active', true)
        .limit(1);
```

**Assumption:** `.ilike` in PostgREST `.or()` expressions uses the `%value%` pattern as a string literal in the filter. This matches the `_orSafe` helper usage elsewhere in the file. Confirmed pattern from `_queryItemsView` line 165.

```javascript
  /**
   * Switch to Inventory tab and pre-filter search to a specific SKU.
   * Used by the low-stock panel "→ ดู" per-item buttons (P7 polish).
   * Pattern mirrors _gotoInventoryLowStock() — polls for lazy-init DOM elements.
   *
   * @param {string} sku  The SKU to pre-fill into the search input.
   */
  function _gotoInventoryItem(sku) {
    try { location.hash = `#inventory?sku=${encodeURIComponent(sku)}`; } catch { /* ignore */ }

    const invBtn = document.querySelector('[data-tab="inventory"]');
    if (invBtn) invBtn.click();

    if (!sku) return;

    // Poll for #inv-search up to ~600ms (10 × 60ms) — Inventory tab is lazy-init.
    let tries = 0;
    const tick = () => {
      const searchEl = document.getElementById('inv-search');
      if (searchEl) {
        searchEl.value = sku;
        // Dispatch input event to trigger AppInventoryTab's debounced search listener.
        searchEl.dispatchEvent(new Event('input', { bubbles: true }));
        return;
      }
      if (++tries < 10) setTimeout(tick, 60);
    };
    tick();
  }
```
